# Upgrading to Magic IndexedDB 3

Version 3 changes schema deployment and migration ownership. It preserves the typed
query interfaces, LINQ translation, ordinary CRUD methods, and the separation between
the C# translation layer and JavaScript engine. The development packages are
`Magic.IndexedDb` and `Magic.IndexedDb.Cli`, both `3.0.0-preview.1`. The intended stable
release is 3.0.0 after the acceptance work is complete.

Do not merge this preview into a release workflow as if it were stable. The existing
release version calculator intentionally accepts stable source versions only. CLI
NuGet publishing still needs its own trusted-publisher configuration and release
step; this PR packages and tests the tool but does not publish it.

## Breaking changes

1. **A table belongs to its declared default database.** Version 2 created every
   discovered table in every discovered database. Version 3 uses `GetDefaultDatabase()`
   plus explicit `Include<T>()` / `Exclude<T>()` membership. Add includes for every
   secondary placement your application uses. `ExplicitTablesOnly()` is available
   when a repository should own the whole membership list.
2. **`IndexedDbSet` declarations are immutable and sealed.** Store the return value
   of each fluent configuration call. Use `WithSchemaId()` for a portable stable ID
   when the physical name includes spaces or other unsupported ID characters.
3. **Existing plain/lossless databases require adoption.** A matching physical layout
   does not grant the engine permission to claim that legacy record values satisfy
   a new contract. Add a reviewed baseline and test real old data.
4. **Model drift fails early.** Runtime changes no longer implicitly change an
   existing database. Export/scaffold a migration and deploy its pinned package.
5. **Opaque custom converters need a versioned contract.** Use `MagicStorageCodec`
   on a custom converter's model/member so representation changes can be detected.
6. **The unsupported `DbStore.DbMigrations` placeholder is a compile error.** Its
   obsolete diagnostic directs callers to this guide. Use `WithMigrations()` and the
   separate CLI instead. No working migration API is being silently reinterpreted.
7. **Scopes initialize on use.** Obtaining a database scope permits read-only
   inspection. `OpenAsync()` or `Query<T>()` performs initialization for that database.
   An unrelated database does not have to initialize successfully first.

The public API baseline is intentionally updated for this major version. There is
no compatibility switch that preserves the old all-tables deployment path alongside
the managed protocol.

## Preserve the old database and continue from its state

First release and retain your final tested 2.x application/package. Capture the
models, serializer behavior, actual native store/index layout, and representative
records for every supported old deployment. A browser inspector can show layout;
it cannot infer C# nullability, converter contracts, enum meaning, or data invariants
from an object-store list.

For an application that previously deployed all discovered tables everywhere,
start v3 with explicit membership matching that physical layout. Include the tables
that happen to exist there even if your app did not query them. Do not remove those
stores merely to make a baseline match a smaller desired schema. A later reviewed
migration can remove a store with explicit data-loss authorization, or preserve it.

```csharp
public static readonly IndexedDbSet Client = new IndexedDbSet("Client")
    .WithSchemaId("clients")
    .ExplicitTablesOnly()
    .Include<Person>()
    .Include<LegacyAuditRecord>()
    .WithMigrations("db/releases/adoption-001/clients/manifest.json");
```

Keep the original physical name, key paths, indexes, numeric format, persisted
property names, and converter representation. Export that compatible model to
`legacy-clients.json`, review it against the real 2.x database, and establish the
initial managed revision:

```sh
magicdb migrations add AdoptV2 --schema legacy-clients.json --database clients
magicdb migrations baseline --database clients --legacy-schema legacy-clients.json --revision 1 --id clients-v2 --acknowledge-data-contract
magicdb migrations validate --schema legacy-clients.json --database clients
magicdb migrations publish --schema legacy-clients.json --database clients --output wwwroot/db/releases/adoption-001
```

The baseline must exactly match the managed schema at its nominated revision. The
acknowledgment records a human-reviewed data-contract claim; it is not proof that
all historical records are valid. Test migration with representative old databases
and your domain assertions. If several baselines have the same native layout but
different field meanings, layout alone cannot distinguish them. The preview refuses
ambiguous matching baselines; design an explicit application-specific transition.

On the first v3 open, the engine verifies the physical schema, increases the native
version, and creates its private journal at logical revision 1. It does not rewrite
existing records during adoption. Subsequent transitions use ordinary migration
history. Clients can skip app releases: retain every transition needed from each
supported baseline. A brand-new client creates the current target schema directly.

This is a preservation path, not a blanket assertion that every old database can be
automatically adopted. Unknown layouts, untracked codec changes, and protected
storage transitions must be resolved explicitly. If a source model change is also
needed, adopt the actual old contract first, then add a distinct transformation.

## Secondary queries and instance names

If this query worked only because v2 deployed everything everywhere:

```csharp
await MagicDb.Query<Person>(person => person.Databases.Employee);
```

Declare the intended placement:

```csharp
public static readonly IndexedDbSet Employee = new IndexedDbSet("Employee")
    .WithSchemaId("employees")
    .Include<Person>();
```

A distinct instance of one schema uses the registered declaration:

```csharp
var local = await MagicDb.Database(AppDatabases.Clients, "account-42-clients");
var people = await local.Query<Person>();
```

Do not create unregistered `IndexedDbSet` objects at query time to smuggle a different
schema or manifest into the same database. Use encryption contexts for account-bound
protected storage.

## Encryption and lossless numeric storage

The ordinary migration engine rejects protected database names and protected field
policies. The current encrypted adapter rejects a migration manifest before opening
or mutating storage. Authenticated encrypted CRUD and its existing policy checks
remain in place, but this preview does **not** claim protected baseline adoption,
key rotation, encryption-policy migration, or encrypted record transforms. Keep
those production databases on the prior supported path until an authenticated
adapter is implemented and validated. Do not remove encryption configuration to
make a migration run.

Within a fixed `lossless-v1` numeric format, ordinary schema/data migrations use the
managed journal and retain the numeric policy guard. Changing between Legacy and
lossless is a separate storage cutover and is rejected as a generic transform.
Follow the [lossless numbers guide](../guides/lossless-numbers.md#existing-databases-and-cutover).

## Build and CI changes

Pin the local CLI in the tool manifest, keep `MagicMigrations` source and
`published.lock.json` in Git, and use the same design-time configuration in developer
and deployment builds. Run model/history validation before publishing static assets,
then run real browser fixture upgrades and application data assertions. CI must fail
on missing tests, unresolved decisions, model drift, changed published bytes,
unsupported features, or failures in the browser matrix.

Read [migration testing](../contributing/migration-testing.md) and the
[implementation handoff](../engineering/v3-handoff.md). A passing schema check cannot
prove custom transforms preserve the meaning of your data.

## Diagnostics

`MAGDB3000` is the compile-time obsolete diagnostic for the old placeholder.
Schema resolver diagnostics use `MAGDB3001`–`MAGDB3013`; they identify invalid
membership, identity, mapping, protection, converter, or canonical JSON contracts.
Runtime routing uses `MAGDB3020` (unregistered database), `MAGDB3021` (table outside
membership), `MAGDB3022` (conflicting declaration/instance), and `MAGDB3023` (plain
instance override requested for a protected database).

CLI diagnostics have stable `MAGDB4xxx` codes and nonzero exit statuses. Browser
errors and structured events use named `MAGDB_*` codes. See the
[CLI guide](../guides/migration-cli.md) and [runtime diagnostics](../guides/migrations.md#diagnostics).
